UI Admin embarquée du kit d'intégration — maquette & spécification

PROPOSITION — aucune implémentation avant validation humaine

Objectif : une console d'exploitation locale, embarquée dans le kit et héritée par toutes les intégrations, qui permet à l'intégrateur tiers (aucun accès aux dashboards internes ShopiMind) de diagnostiquer et opérer son instance sans jamais ouvrir le SQLite : santé, installations, provisioning, curseurs, runs, webhooks, idempotence, dead-letter des rejets — et les actions associées, sécurisées et auditées.

Frontière assumée : 100 % côté intégrateur. Cette UI appartient au kit, donc à l'intégration : elle tourne dans son runtime, lit uniquement le store SQLite local de l'instance, ne fait aucun appel aux services ShopiMind et n'exige aucun compte ShopiMind. La supervision côté ShopiMind (agrégée multi-boutiques, sur la base core) est un monde séparé : ici, aucun identifiant interne ShopiMind — uniquement les installation_id opaques déjà présents dans le store.

0. Résumé exécutif — mes arbitrages (le « patron » du kit)

  1. Correction du brief : le runtime du kit est Hapi (@hapi/hapi), pas Fastify. Tout le reste de l'inventaire du brief correspond bien à la v1.4.0 (tables jusqu'à rejected_item, endpoints /admin/overview & co — livrés par le LOT E).
  2. UI = un client de l'API JSON, jamais du SQL. L'UI (une seule page autoportante servie sur GET /admin/ui) consomme exclusivement /admin/*. La surface testée et sécurisée est l'API ; l'UI n'a aucun privilège propre. Tout ce que l'UI montre est scriptable en curl.
  3. Session navigateur digne de ce nom : page de connexion → le jeton admin est échangé contre un cookie de session HttpOnly + SameSite=Strict (TTL 12 h glissant, invalidé au redémarrage). Le jeton ne vit jamais dans l'URL ni le localStorage. CSRF sur toutes les mutations. L'auth existante par en-tête (x-admin-token/Bearer) reste valable pour les scripts — rétrocompatibilité totale.
  4. PII masquée par défaut, révélation auditée. Les payloads (rejected_item, webhook_log) sont servis masqués (emails, téléphones, adresses). « Révéler » est un POST par item, confirmé, journalisé dans un nouvel audit_log.
  5. Secrets : présence seulement. L'écran État affiche clé · chiffré ✓ · date. La valeur d'une ligne encrypted=1 ne quitte jamais le serveur (l'endpoint ne la lit même pas).
  6. « Rejouer un rejet » — sémantique honnête. Re-pousser tel quel un payload stocké est un piège (donnée périmée ; la source de vérité est le système partenaire). V1 : Purger (item ou filtre) + « Re-synchroniser l'entité » (relance la fenêtre couvrante via le moteur — le bon geste après correction de la cause). V2 optionnelle : hook replayRejected(ctx, item) déclaré par l'intégration, pour un vrai rejeu item par item quand l'intégration sait le faire.
  7. Exposition isolable : nouvelle option adminPort/adminHost → un second listener Hapi dédié à /admin/* + UI, bindable sur un réseau interne, séparé de l'ingress public des /webhook. Par défaut (option absente) : même port qu'aujourd'hui (compat), avec guidance ferme de firewalling.
  8. Zéro dépendance : UI vanilla (HTML/CSS/JS inline, ~70–90 kB), CSP stricte par nonce, aucun CDN, aucune lib front. Embarquée dans dist/ via un script de génération (même philosophie que les migrations SQL embarquées).
  9. Ajouts au-delà du brief (mon initiative) : écran Audit (le journal des actions est lisible dans l'UI elle-même) ; badge backoff sur les curseurs (la colonne consecutive_failures E3 existe, montrons-la) ; mode full/incrémental ajouté au résumé de run (aujourd'hui non tracé) ; compteur de rejets dans la nav (la vue phare doit crier).

5. Modèle de sécurité

5.1 Authentification & session

  • Deux modes, un seul secret : (a) scripts/API : en-têtes x-admin-token/Bearer, inchangés (rétrocompat totale) ; (b) navigateur : POST /admin/session échange le jeton contre un cookie de session spm_admin_sid — HttpOnly, SameSite=Strict, Secure (si TLS), Path=/admin.
  • Sessions en mémoire (Map id→{expiry, csrf}) : id 256 bits aléatoires ; TTL 12 h glissant ; invalidées au redémarrage du process (re-login — acceptable pour un outil d'exploitation) ; ≤ 20 sessions simultanées (éviction LRU).
  • CSRF : défense en profondeur — SameSite=Strict + jeton CSRF par session injecté dans la page, exigé en en-tête x-csrf-token sur toute mutation + vérification Origin/Sec-Fetch-Site.
  • Anti-bruteforce : limiteur dédié au login (5/min/IP) en plus du limiteur admin existant ; échecs journalisés (login_failed).
  • Force du jeton (kit public = sûr par défaut) : contrôle au démarrage — ADMIN_TOKEN < 16 caractères → refus de monter l'admin ; < 32 → avertissement bruyant. La doc recommande openssl rand -hex 32.

5.2 Secrets & PII

  • Secrets : l'endpoint « état » exécute SELECT key, encrypted, updated_at, length(value) — la colonne value d'une ligne chiffrée n'est jamais lue, donc jamais déchiffrée, donc jamais transmissible. Test d'invariant dédié.
  • PII : masquage serveur par défaut sur les payloads affichés (emails m•••@•••.fr, téléphones, champs nominatifs — réutilise redact() + motifs email/téléphone). La révélation est unitaire, confirmée, auditée, non cacheable. Les payloads de webhook_log sont déjà expurgés à l'écriture (schéma sensible) — double filet.
  • Rétention (RGPD) : purge quotidienne existante (retentionDays, défaut 90 j) appliquée à webhook_log, webhook_seen, inbound_event, rejected_item ; audit_log a sa propre rétention (365 j, configurable).

5.3 Exposition réseau & en-têtes

  • Isolation : option adminPort (+ adminHost, défaut 127.0.0.1 quand adminPort est posé) → second listener Hapi qui porte seul /admin/* + /admin/ui ; le listener public ne sert alors plus que /webhook/*, /inbound/*, /health. Sans l'option : même port (compat), la doc exige un firewalling de /admin à l'ingress et le kit émet un avertissement bruyant au démarrage (« admin UI servie sur le listener public — utilisez adminPort ou une allowlist à l'ingress »).
  • Rate-limit derrière proxy — limite documentée : l'IP vue est celle du proxy (le kit ne lit pas X-Forwarded-For, spoofable par défaut). Limite préexistante du kit, documentée dans le guide « Operate » ; une option trustProxy pourra venir plus tard si un besoin réel l'exige.
  • CSP stricte par nonce : default-src 'none'; script-src 'nonce-…'; style-src 'nonce-…'; img-src 'self' data:; connect-src 'self'; frame-ancestors 'none'; base-uri 'none'; form-action 'self' + X-Content-Type-Options: nosniff, Referrer-Policy: no-referrer, Cache-Control: no-store sur toutes les réponses admin.
  • Multi-tenant : chaque endpoint de détail est scopé par installation_id (paramètre de chemin) ; aucune jointure inter-installations ; l'agrégat (overview) n'expose que des ids opaques + domaines déjà connus de l'intégrateur. Tests de scoping (une installation A ne peut pas lire les rejets de B via un id forgé — chaque requête filtre WHERE installation_id = ?).

6. Architecture technique & API

6.1 Principe

Navigateur ──(cookie session + CSRF)──▶ /admin/ui (HTML unique, nonce CSP)
                                        /admin/*  (JSON — la SEULE couche données)
Scripts/CI ──(x-admin-token / Bearer)─▶ /admin/*  (inchangé)
UI = fetch() vanilla → tableaux rendus à la main (~600 lignes de JS, 0 dépendance)

6.3 Stack front & embarquement

  • Vanilla : un fichier src/admin-ui/ui.html (source de vérité, éditable), CSS variables (thème clair/sombre via prefers-color-scheme + toggle persisté localStorage — préférence d'affichage uniquement, jamais de secret), dictionnaire i18n fr/en embarqué (~120 clés), fetch() + rendu DOM manuel, auto-refresh 30 s (Page Visibility API : pause si onglet caché).
  • Embarquement dans dist/ : script scripts/embed-admin-ui.mjs (prebuild) qui génère src/http/admin-ui.generated.ts (export const ADMIN_UI_HTML = "…" + KIT_VERSION depuis package.json). Même philosophie que les migrations SQL embarquées : aucun asset à copier, files:["dist"] inchangé. Empreinte : ~70–90 kB bruts dans le bundle.
  • Activation : l'UI n'est montée que si adminToken est configuré (comme les routes admin aujourd'hui) ; option adminUi: false pour la désactiver explicitement.

Tests de sécurité exigés (vitest — invariants)

  1. 401 sans jeton ni session sur chaque route /admin/* (paramétré sur la table des routes) ; 401 aussi avec cookie forgé/expiré.
  2. Mutations sans en-tête CSRF → 403, même avec session valide.

  5. Scoping : les rejets/curseurs/runs de l'installation B n'apparaissent jamais sous l'id A.
  6. Login : 6ᵉ tentative en 1 min → 429 ; login_failed audité.
  7. Rétrocompat : les 5 endpoints existants répondent à l'identique avec l'auth en-tête (snapshots).
